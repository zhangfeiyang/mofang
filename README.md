# Cube AR

离线运行的 Android 三阶魔方扫描与实时还原指引 App。

## 克隆与 LFS

仓库内的演示视频（`video_20260816_*.mp4`）通过 [Git LFS](https://git-lfs.github.com) 存储。克隆后默认看到的是 LFS 指针（约 130 字节），需要安装并拉取 LFS 对象才能拿到真实文件：

```bash
# 一次性安装
sudo apt install git-lfs        # Debian/Ubuntu
# brew install git-lfs           # macOS
git lfs install

# 克隆仓库并拉取 LFS 文件
git clone git@github.com:zhangfeiyang/mofang.git
cd mofang
git lfs pull

# 已克隆后单独刷新 LFS
git lfs fetch && git lfs checkout
```

如果你只关心源码而不在意演示视频，可以不装 LFS；构建 APK 不依赖视频。

## 使用

1. 安装 APK，允许相机权限。首次打开会有一页使用说明，之后点右上角 **?** 随时再看。
2. **扫描**：把魔方的一个面正对镜头，整个面露出来。App 会在画面任意位置找到这个面，把 AR 网格贴到贴纸上；
   网格外框被一圈薄荷绿描满即采集成功（闪光 + 震动）。依次露出其他面，顺序和握持角度都不限。
   底部的**展开图**实时显示每个已采集面读到的颜色；还没采的面只显示它的中心色，告诉你接下来该转哪个颜色。
   光线暗时点右上角的**补光灯**；手指挡住色块、离得太远时底部会直接提示。
3. **五个面即可**：第六面由棱、角块的唯一性推算（展开图上用虚线框标出）；扫到六个面则直接做全局校验。
4. **核对**：识别完成后展示整个魔方的展开图和总步数。颜色对上了点「开始还原」，不对就「重新扫描」。
5. **还原**：右上角的 3D 小魔方循环演示当前这一步，底部是大号转动记号、颜色说明和接下来几步。
   把要拧的那一面对准镜头时，画面上还会叠一个指示方向的环形箭头。镜头看到动作完成会自动进入下一步；
   也可以随时点「上一步 / 下一步」，或者用**音量键**（下 = 下一步，上 = 上一步），两手不用离开魔方。
   默认语音播报每一步（右上角喇叭可关）。

App 按常见配色映射中心块：白 U、红 R、绿 F、黄 D、橙 L、蓝 B。转动记号：R 表示红色中心面顺时针 90°
（正对该面看），R′ 是逆时针，R2 是 180°。纯绕竖轴一圈只能看到四个侧面，不够恢复 54 个色块，
因此至少还要展示顶面或底面之一；第六面可由结构推算，不必再翻到底。

## 训练检测模型

网络是一个轻量 encoder-decoder（`CubeFaceNet`）：整帧按 160×288 拉伸送入，四个角点由 spatial-softmax 热力图回归，另有一个 presence 头判断画面里有没有朝向镜头的面。输出与 App 里 `CubeFaceModel` 的 ONNX 约定一致（`corners` 8 个数 + `presence`）。

### 当前模型（`models/v2`）：合成 + 真机混训

```bash
# 1. 真机打包（frames/ 下两个视频目录都叫 frame_000001.jpg，不能直接混拷）
python3 scripts/pack_real_dataset.py --frames frames --out data/real_cubes

# 2. 把训练集帧里的魔方抠掉（inpaint），当作合成渲染的真实背景：桌面、键盘、手
python3 tools/make_backgrounds.py --real data/real_cubes --out data/backgrounds

# 3. 6 万张合成帧，75% 画在真实背景上
python3 tools/synth_cube.py --count 60000 --size 160 --height 288 --workers 7 --seed 7 \
    --out data/synth_v2 --backgrounds "data/backgrounds/*.png"

# 4. 混训：真机训练集每个 epoch 重复 80 次（否则 85 帧在 5.7 万张渲染里只占 0.15%），
#    按真机验证集选 checkpoint
python3 tools/train_detector.py --data data/synth_v2 --real data/real_cubes --real-repeat 80 \
    --epochs 30 --batch 96 --lr 2e-3 --width 1.5 --workers 6 --out models/v2
cp models/v2/cubeface.onnx app/src/main/assets/
```

`data/synth*/` 和 `data/backgrounds/` 是生成数据，不进 git。真机图可以先缩到一半（540×960）再训，
增强的 CPU 开销降为四分之一，精度不受影响。

| 21 帧真机验证集 | 旧模型（只用 85 帧真机训） | 合成初版 | **v2** |
|---|---|---|---|
| 贴纸中心误差中位数（贴纸间距） | 0.44 | 0.20 | **0.13** |
| 误差 < 0.4 间距的帧 | 43% | 94% | **100%** |
| 旧取样器能完整读出的面 | 9 / 21 | 16 / 17 | **17 / 17** |

（「贴纸间距」= 相邻两块贴纸中心的距离；误差超过约 0.4 个间距，取样点就会落到黑边或隔壁贴纸上。）

### 两个影响很大、但不直观的约束

- **合成画布比例必须等于部署画面比例。** 用方形训练、竖屏部署会让真实帧检测率从 19/22 掉到 9/22。
- **正面占优阈值（`MIN_FACE_DOMINANCE`）是召回与精度的直接权衡。** 接近 45° 时两个面投影面积相近，
  「最大的面」会在两者之间跳变，几乎相同的画面会带上不同面的角点。设为 1.10（≈42°）时漏检约 5%，
  代价是极端倾角下网络会给出跨两个面的四边形。旧版靠把 `PRESENCE_THRESHOLD` 提到 0.85 挡掉；
  现在跨面四边形要先过格点精定位和一致性检查才可能被采集（见「实现」），所以阈值降到 0.6，
  只负责过滤没有魔方的帧：held-out 帧检出 20/21，0.85 时只有 17/21。

## 实现

### 识别

- CameraX `Preview` + `ImageAnalysis`（RGBA，全画面），丢弃积压帧，分析帧间隔下限 45 ms。
- **CNN 粗定位**当前朝向面的四个角点（`CubeFaceModel`，ONNX Runtime，1.3 MB）。输入按 OpenCV `INTER_AREA`
  的面积平均缩放（`AreaResizer`，纯 Java，与 OpenCV 逐像素一致）。启动时 NNAPI 和 CPU 各跑几次推理，
  谁快用谁——这么小的网络在不少手机上 NNAPI 反而更慢。
- **格点精定位**（`FaceRefiner`）：按粗四边形把面附近区域透视矫正成 160×160 小图，大津阈值分出贴纸与黑色塑料，
  找出贴纸块，再拟合 3×3 格点。每个块按「是否方正、大小是否和同伴一致、是否落在格点上」加权——
  隔壁面的贴纸矫正后是被压扁的，滑出一行的窗口会因此失去那一行的权重。拟合在自己矫正出的小图上
  迭代三次，最后一次还在移动的拟合视为没有锚定、直接拒绝。真机标注帧上贴纸中心误差中位数约 0.08 间距。
- **一致性检查**：精定位结果与 CNN 四边形的贴纸中心平均相差超过 0.4 间距时，两者必有一个跨了面或认错了面，
  这一帧只显示、不采集。这一条把单帧精定位滑行的错误（演示视频上约 13% 的帧）挡在了采集之外。
- 精定位以上一帧的格点为起点（CNN 中心仍在同一个面上时），比网络的粗角点准得多。
  CNN 连续 3 帧拒绝时，`AnchorSearch` 从上次位置和几个常见的握持位置直接搜格点，代替原来的 OpenCV 轮廓兜底。
- 取样（`FaceSampler`）：精定位后的格子在 0.92 倍偏移处取 0.22 格宽的块（外圈贴纸最外缘是棱边阴影和反光）；
  粗四边形则内缩 0.84、取 0.10 格宽的小块，保证角点差三分之一块时仍落在贴纸上。每格取中位数，
  离散度过大（手指、反光、压到格线）标为不可信。
- **采集门槛**（`CaptureGate`）：争议帧不采；没有精定位的帧中心必须像贴纸（饱和，或明亮且中性）——
  精定位失败多半是手指挡住了面，拇指压在中间会读出一个平整「可信」的肤色中心。
- 稳定判定按 **Lab 原始读数**而非颜色名称；两帧一致且时间跨度 ≥ 90 ms 才采集——30 fps 下相邻两帧
  几乎一样，按帧数判定会让扫过去的跨面读数也算「稳定」（演示视频上错误采集从 6% 升到 9%）。
  容忍连续 2 帧掉帧；稳定期内的多帧读数取平均。
- 距离下限（`MIN_CAPTURE_SIDE_FRACTION`）：魔方最短边不足画面短边 8% 时只跟踪不采集，并提示拿近。

### 装配与求解

- 颜色**不做逐格阈值判定**。每格只记录 CIELAB 原始读数，集齐后以六个中心块为本次扫描的颜色原型，在
  「每色恰好 9 块」的硬约束下用匈牙利算法做全局最优指派。实拍中红与橙的色相只差 2–4°，固定阈值必然从
  色块簇中间劈开，而 Lab 下两者相差约 30 个明度单位。
- 面的分组用**相对**规则（占整池色彩跨度的比例，带下限），绝对色差阈值会让两个面永久互撞、扫描卡在 5 面。
  分组宁可分多也不合并。聚类结果缓存到观测池变化为止（原来每次 `put` 和每帧刷新 UI 都要重算一遍 O(n⁴) 的聚类）。
- **一个颜色组至少两次观测才算采到一个面**，面数、进度点和是否可以推算全部按这个口径。只看到一次的组
  多半是跨面读数或手指，原来它会占掉一个「面」的名额：界面显示 6 面但其实缺一面，五面推算也因为
  「组数不是 5」而拒绝运行。
- 多于六组时丢弃**观测次数最少**的组；池子满了先驱逐被丢弃组和只出现过一次的观测，再驱逐最大组最老的观测，
  最新一条永远不驱逐。原来按置信度排序——跨面读数九格平整、置信度反而最高，曾经把一个有 7 次观测的真面
  整组驱逐，颜色就此消失。
- 同一个面的多次观测**先按 roll 对齐再逐格取中位数**合成一条读数，不挑「置信度最高」的那条。
- 六面校验的朝向搜索边放边查：每放好一个面，就检查刚刚完整的棱块、角块是否合法且不重复，
  错误朝向在第一块就被剪掉，不再对 4⁶ 种组合逐一跑完整校验。
- 五个面即可还原：第六面的九个色块由棱、角块的唯一性填出；填法不唯一时拒绝猜测、继续扫描。
  一旦找到两种合法填法就立即停止搜索（结论已经是「不唯一」）。
- 每次装配有时间上限（五面 0.4 s、六面 1.5 s）：读数互相矛盾的池子原来每次要磨好几秒，下一次更好的
  尝试只能排队；尝试会随新观测反复进行，所以超时放弃几乎没有代价，也不计入「池子被污染」的判定。
- 装配在后台线程的**观测池快照**上进行，扫描线程继续往活池子里加观测，互不干扰。
- 连续 3 次六面校验（非超时）都失败才判定池子被污染——通常是扫描途中拧了某一层——这时清空重扫。
  失败时把整池读数写到 `getExternalFilesDir(null)/scan-fail.json`，可用 `adb pull` 取回离线复现。
- 内置 MIT 许可的 `min2phase` 两阶段求解器，全程离线；启动时在后台预建剪枝表，第一次求解不卡。

### 还原引导

- `MoveTracker` 按镜头看到的画面推进步骤。旧逻辑比较「被拧的那一面」拧之前和拧之后、但忽略旋转——
  而拧一个面只会让它自己的贴纸转 90°，前后是同一个图案，所以只要把目标面稳稳地对着镜头两次就会
  自动跳一步。现在用两类真正能区分状态的证据：被拧面的四个邻面（换掉一行/一列，任何旋转下都能认出）；
  以及被拧面本身——记住它在这一步里被看到时的旋转，镜头不动而图案转了 90° 才是拧了。
- 向后看 3 步：镜头漏看了一两步也能追上。画面与任何预期状态都对不上时提示可能拧错了，可以点「上一步」。
- 引导阶段的九宫格颜色按本次扫描的调色板命名（`ScanPalette`），红/橙不会在屏上闪错；
  只推算过的第六色在第一次被看到时补进调色板。

### 界面

- 相机画面 + 画布 AR 层（`CubeOverlayView`）+ 普通 View 的 HUD。AR 网格以显示帧率向最新检测结果滑动
  （检测本身只有 10–20 Hz），角点顺序按循环对齐，网格不会因为检测器换了起始角而转圈。
- 采集进度画在网格外框上，不再画一个比面还大的外圈。
- 3D 引导魔方修了三个老问题：面片数组越界（`n += emitCubie(n, …)` 把下标翻倍，进入引导就会崩溃）、
  缩放把魔方画到卡片外、贴纸和塑料壳同平面时深度排序随机——现在做背面剔除和简单光照。
- 全面适配 edge-to-edge（targetSdk 35）；HUD 按系统栏留边。

相机帧不保存、不上传，也不需要网络权限。
